# Dataset releases and partition management

The committed catalog contains 38 development scenarios and no held-out cases.
Development scenarios include original normal/multi-step, recovery, injection,
authorization and ambiguous-task cases. Their identities and fixture hashes are not
regenerated by the product demo.

A SplitManifest pins template IDs, family IDs, scenario versions/content hashes and
split assignment. A DatasetRelease pins the development and held-out manifest IDs
and hashes together with the complete assignments and validation version. Registration
checks both partitions, not one manifest in isolation. Overlapping families/templates/
scenarios, substitutions, missing partitions and changed hashes are rejected. Artifacts
are immutable and versioned; revisions require a new reference.

Validate the committed schemas without writing a database:

```console
uv run --locked opsdesk-research validate benchmarks/research/split-development.json
uv run --locked opsdesk-research validate benchmarks/research/split-held_out.json
uv run --locked opsdesk-research validate benchmarks/research/dataset-release.json
```

After authorized registration, `opsdesk-research --scope STUDY verify-release FILE`
verifies referenced frozen partitions. Use templates/README.md for independently
sourced held-out authorship. Copying or paraphrasing development scenarios cannot
establish family independence. An empty held-out manifest is a legitimate missing
research prerequisite, not evidence of generalization. Candidate pairing requires
the exact registered dataset-release reference and compatible oracle/scenario hashes.
